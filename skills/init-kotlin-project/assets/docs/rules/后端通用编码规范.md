# 后端通用编码规范

适用 `${PROJECT_NAME}-web` 下所有 Kotlin / Java 代码。

## 1. 分层与控制器

- 用 Spring MVC `@RestController`（返回 JSON/API）或 `@Controller`（页面渲染），配合 `@GetMapping`、`@PostMapping` 等映射注解。
- 简单逻辑采用简化控制器：单一请求处理逻辑（如"获取单个用户信息""返回静态数据"）直接写在控制器方法中，避免过度分层。
- 不要过度封装方法，除非业务功能一致可复用；优先使用已有 SDK，如 Date 解析与格式化用 hutool `DateUtil`。

## 2. 参数校验（JSR-380）

- 用 `@NotNull`、`@NotBlank` 等注解定义规则，通过 Spring `@Valid` 触发校验；禁止在控制器手写校验逻辑。
- 入参已由 JSR-380 完成基础校验（非空、范围、长度、枚举等）时，Service 层禁止重复同类校验；Service 只保留业务校验：存在性、唯一性、权限、并发冲突、状态机约束。
- 列表查询等 API 入参中类型、状态相关条件优先用枚举类型接收，减少 Service 层冗余类型校验。
- 不使用兜底编码思想（如 Kotlin `coerceAtLeast`），按业务语义显式处理。

## 3. 命名

- 普通方法遵循主谓宾。
- 检查类方法用 `check...()`；校验类用 `validate...()`；业务核心方法用 `...core()`；API 出入参 DTO 构建用 `build...()`。
- 包名全小写、多词直接连写，不用驼峰、大写或下划线，例如 `checkinpoint`、`checkinmap`。
- 同一业务模块在 `controller`、`service` 等各层使用相同包名，例如 `controller/client/checkinpoint` 与 `service/checkinpoint`。
- 变量与函数用 camelCase，名称具描述性。

## 4. 注释

- `private` 方法必须添加方法描述。
- 核心方法调用处加简要注释说明业务约定，格式 `// 业务约定....`；不要逐行注释。

## 5. 日志

- 统一通过 `import com.qingyan.extension.extension.logger` 获取 logger。
- 提交、状态流转、外部调用、失败等关键节点必须记录日志，使用 `log.info` / `log.warn` / `log.error`：

```kotlin
log.info("订单支付,请求3方,orderNo:{}\nrequest:{}", data.orderNo, data.toJSONString())
```

## 6. Kotlin 语法

- 灵活使用 `.apply`、`.run`、`.let`、`.also` 等作用域函数。
- if / else 分支内业务代码只有一行时可省略 `{}`。

## 7. 有赞平台能力前置确认

涉及服务端有赞扩展点、消息、开放 API 等平台能力时，**设计与编码前**必须先按具体需求从 <https://doc.youzanyun.com/llms.txt> 检索并查阅对应能力文档，确认能力是否支持、接入方式、参数与数据结构、平台差异及使用限制；不得凭已有经验或项目现状推断平台能力。

新增有赞能力只放 `com.youzan.cloud.${PACKAGE_NAME}.open.youzan`：

| 能力 | 包路径 |
| --- | --- |
| 扩展点实现 | `open/youzan/extension` |
| 事件消息处理器 | `open/youzan/message` |
| 开放 API 客户端与消息桩 | `open/youzan/api` |

`thirdside` 只放**非有赞**的三方系统对接。
