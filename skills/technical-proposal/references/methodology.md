# 方法论：技术方案是施工图

## 判断标准

把文档单独交给 AI coding agent，它能否不问人就把代码写出来。能，就是施工图；不能，说明关键信息还在人脑或别的文档里。

三条原则：

- **自包含**：AI 的输入边界就是这一份文档。表结构、模块职责、错误码、约定都当场写全。
- **事实先于设计**：能力未核验，不写架构、表和接口。结论只能是可用 / 受限 / 不可用 / 待确认，并附依据。
- **可回查**：需求回到 PRD 标题 + 行号，能力回到官方依据，风险回到具体故事。

## 骨架

| 段 | 章节 | 作用 |
|-|-|-|
| 防错 | 2.1–2.3、3 | 锚定需求、框定范围、澄清歧义、核验能力 |
| 框定 | 4.1 | 划清模块边界和已定决策 |
| 施工 | 5–7 | 表、接口、核心链路 |
| 收口 | 8、附录 B | 登记后果、挂上依据 |

顺序固定：需求 → 事实 → 设计 → 后果。

## 六条硬要求

1. **需求锚定**：每条需求写 PRD 标题 + 行号；R1/R2 只是文档索引，不能替代行号。每个故事至少一行需求；2.2 同时写“要做”和“不做”。
2. **模块可落地**：4.1 给 M 编号、Service / 类命名和职责。职责必须写“不负责什么”；后端用 `XxxService`，前端用 `XxxPage` / `XxxComponent`。架构由模块表 + 时序图参与者表达，不强制单独画架构图。
3. **表结构可直接建表**：独立 DDL 文件 + 文档内每张表的完整 `CREATE TABLE` 代码块，段号一致。金额用分（bigint），时间用 `datetime(3)`；枚举、状态机、幂等键、唯一键落到约束上。DDL 由 AI 出草稿，人修剪命名、类型和多余字段。
4. **时序图是技术密度下限**：必须画出并发（锁粒度 / key）、幂等（重复请求 / 回调）、状态机（合法 / 非法迁移）、异常补偿（超时 / 失败 / 回滚 / 告警）。只画 happy path 视为没写完。参与者对应 4.1 的 M 编号，节点标 `【S1】`。
5. **风险是后果登记**：写清兼容性、异常兜底、技术债、运营成本，并标归属故事、是否阻塞、应对措施。不要写成“待确认清单”。
6. **澄清项可执行**：写清找谁确认、何时确认、不确认影响什么。

## 多故事

谈到技术方案，总会讨论是按项目拆大纲还是按故事拆，
- 按项目拆：整篇文档太大太多，评审和阅读费力气
- 按单故事拆：有些故事非常小却要列一整个大纲非常浪费

所以多故事来了：

- 两个故事共享至少一张表或一个接口 → 同一份方案；否则拆开。
- 一份方案覆盖 3–6 个故事、正文 ≤15 页（DDL 代码块不计），包含一条端到端链路。
- 多故事只加四个坐标：2.1 故事列；4.1 模块编号 + Service 命名；8 风险归属故事 + 是否阻塞；5 独立 DDL 文件 + 文档内 `CREATE TABLE`。
- 共享表只设计一次；每个故事节独立可读，公共层只写一次，故事编号稳定。

## 反模式

- 把整个项目塞进一份方案，或一个故事写半页。
- 按“同一个大需求”合并，而不是按共享表 / 接口判断关联。
- 用自编编号替代 PRD 行号。
- 能力没核验就写架构和表结构。
- 只画成功链路，缺锁、幂等、状态机和补偿。
- 风险写成待确认项，没有归属和兜底。
- 只列表名和字段清单，没有 `CREATE TABLE`。
- 模块只写“订单服务 / 商品配置”，没有 Service 命名。

## 好方案的标准

结论摘要能在 30 秒内说清做什么、关键结论、不做什么。AI 能直接建表、写接口、实现状态流转和异常处理；评审能快速挑错；QA 能按故事逐条验收；运维能看到告警、补偿和回滚。
