# 质量门：交付前逐项过

用法：写完后按下面顺序逐项检查。每项标 `PASS` / `FAIL` / `N/A`；`FAIL` 要么修，要么在交付说明里明确写成“已知缺口 + 不修的原因”，不要静默跳过。

## A. 范围与批次

- [ ] A1. 文档顶部写清了需求来源、所含故事、适用商家。
- [ ] A2. 所含故事是“关联故事”，不是按大需求硬凑；每个故事能独立验收。
- [ ] A3. 故事数在 3–6 个、正文 ≤15 页（DDL 代码块不计页数）；超过时已按上线批次拆分，而不是继续加内容。
- [ ] A4. 2.2 同时写了“要做”和“不做”；“不做”是具体的，不是“其他”。
- [ ] A5. 依赖但不属于本文范围的内容，已明确列出。

## B. 需求锚定

- [ ] B1. 2.1 每一行都有 PRD 标题 + 行号，且行号可回查。
- [ ] B2. 2.1 每一行都有“故事”列，能落回 S1 / S2 / S3。
- [ ] B3. 每个故事至少有一行需求；没有需求的故事不应出现在“所含故事”里。
- [ ] B4. 编号（R1、R2…）只作文档内索引，没有被当成 PRD 定位使用。
- [ ] B5. 2.3 的待确认项写了“找谁确认 / 截止时间 / 不确认的后果”，没有只写 TBD。
- [ ] B6. 文档里没有“根据经验 / 一般来说 / 应该需要”这类无法回查的需求断言。

## C. 能力事实

- [ ] C1. 方案依赖的每个有赞能力、三方能力都有核验记录。
- [ ] C2. 每条结论是四种状态之一：可用 / 受限 / 不可用 / 待确认。
- [ ] C3. 每条“可用 / 受限”都有验证方式和依据链接；“待确认”有确认人和影响说明。
- [ ] C4. 能力核验排在总体架构之前，没有出现“先设计、后补核验”。
- [ ] C5. 没有用“应该可以 / 理论上支持 / 之前好像用过”替代核验。

## D. 架构与模块

- [ ] D1. 4.1 只列本方案涉及的模块，没有把整个系统画进来。
- [ ] D2. 每个模块有稳定编号（M1…Mn），全文引用一致。
- [ ] D3. 每个模块的职责里写了“不负责什么”，边界可判断。
- [ ] D4. 时序图里的每个参与者都能对上 4.1 的模块编号或明确的外部系统。
- [ ] D5. 已定决策写在 4.1 的“决策”列，没有藏在正文段落里。
- [ ] D6. 4.1 有“Service / 类命名”列，后端模块落到 `XxxService`，前端模块落到 `XxxPage` / `XxxComponent`；没有用“商品配置 / 支付网关”这类泛称代替。

## E. 数据模型

- [ ] E1. DDL 有独立文件，文件名、目录、段号引用规则写清。
- [ ] E2. 文档里的 DDL 段号与 SQL 文件注释一致。
- [ ] E8. 5 节为每张表给出了完整的 `CREATE TABLE` SQL 代码块（以 `-- §DDL-n` 开头），不是只写表名、字段清单或段号引用；字段、类型、注释、默认值、唯一键、索引齐全，并能直接复制建表。
- [ ] E3. 每张表写了用途、所属故事、新增 / 改造。
- [ ] E4. 金额用分（bigint），时间用 `datetime(3)`，主键 / 租户 / 软删 / 索引命名统一。
- [ ] E5. 状态机、枚举、幂等键、唯一键落到了表或约束上，不是只在文字里。
- [ ] E6. 共享表只设计一次；其他故事只写差异，没有重复建表。
- [ ] E7. DDL 是“AI 草稿 + 人砍三刀”的产物：命名、类型、无用字段都已修剪。

## F. 接口

- [ ] F1. 接口表包含编号、方法、路径、说明；共享接口在说明里标“首次定义 / 复用 Bx”，并带故事编号。
- [ ] F2. 共享接口在首次出现处写全，其他位置只写“复用 Bx”。
- [ ] F3. 路径、方法、鉴权方式与项目现有约定一致。
- [ ] F4. 重点接口有请求 / 响应示例，字段名和类型具体。
- [ ] F5. 错误码、幂等语义、超时 / 重试策略已明确。
- [ ] F6. 接口与 2.1 的需求、4.1 的模块能对应上，没有孤立接口。

## G. 时序与异常

- [ ] G1. 核心链路时序图覆盖了主路径，不是只有一句“调用成功”。
- [ ] G2. 并发：锁的粒度、key、失效处理已落到图上。
- [ ] G3. 幂等：重复请求 / 重复回调 / 重复支付有识别与处理。
- [ ] G4. 状态机：状态、合法迁移、非法迁移处理已画出。
- [ ] G5. 异常补偿：超时、失败、回调丢失、金额不一致、部分成功有收口。
- [ ] G6. 每个节点标注了所属故事 `【S1】`，多故事文档可分段阅读。
- [ ] G7. 只画 happy path 的时序图视为未完成；至少有一个 `alt/else` 异常分支。

## H. 风险与附录

- [ ] H1. 风险项是“后果登记”，不是“我不知道什么”的待确认清单。
- [ ] H2. 每条风险有归属故事。
- [ ] H3. 每条风险标了是否阻塞上线。
- [ ] H4. 每条风险有应对 / 兜底或触发信号，不是只描述问题。
- [ ] H5. 兼容问题、异常兜底、技术债、运营成本至少各被考虑过一次。
- [ ] H6. 附录 B 的链接可访问，且确实是本方案引用的官方文档。

## I. 自包含与可读性

- [ ] I1. 关键内容均为直接描述，没有只给引用出处、让读者自行跳转查看的情况。
- [ ] I2. 需要的表结构、模块职责、错误码、约定在本文内能直接找到；表结构至少要有完整 `CREATE TABLE` 代码块，不能只靠独立 SQL 文件传递。
- [ ] I3. 多份文档之间最多有一个几行索引做导航，索引不承担内容传递。
- [ ] I4. 结论摘要能在 30 秒内说清“做什么、关键结论、不做什么”。
- [ ] I5. 表格优先于长段落；没有大段重复描述。
- [ ] I6. 读者不需要作者的脑内上下文就能读懂。

## J. 交付物完整性

- [ ] J1. 技术方案 `.md` 已写入约定目录（默认 `docs/技术方案/`）。
- [ ] J2. DDL `.sql` 已写入同目录，文件名与文档引用一致。
- [ ] J3. 文档内没有残留的占位符（`{...}`、`[ ]`、`TODO`），除非明确标为待确认。
- [ ] J4. 交付说明写清了覆盖故事、待确认项、下一步最该确认的三件事。

## 评审已有方案时怎么输出

用户让你 review 一份现成方案时，不要只给“整体不错”。按严重程度输出：

1. **阻塞**：需求无法回查、能力结论无依据、时序缺关键异常分支、数据模型无法支撑主链路。
2. **高风险**：范围蔓延、模块边界不清、幂等 / 并发 / 状态机有漏洞、风险没有兜底。
3. **建议**：结构、可读性、字段补充、链接整理。

每条发现写：位置（章节 / 行号）、问题、证据、建议怎么改。用户明确让你改时再动文件；只让你 review 时不要改原文件，把改法写清楚。不能替用户决策的，标成待确认。

## 常见失败对照

| 症状 | 大概率原因 | 修法 |
|-|-|-|
| 文档很长但 AI 还是写错 | 缺数据模型 / 接口 / 异常分支 | 补 5、6、7 节，不要加形容词 |
| 评审看不出问题，上线后全是问题 | 风险写成了待确认清单 | 改成后果登记，补归属故事和兜底 |
| 两个故事的表结构冲突 | 没有先做共享层收敛 | 先建“故事 × 表 / 接口”矩阵，共享表只设计一次 |
| 需求对不上 PRD | 用了自编编号，没做行号锚定 | 回 PRD 补标题 + 行号，对不上的删掉 |
| 能力核验写了“应该可以” | 没查官方文档 / 没验证 | 改成“待确认”，补确认人和影响 |
| 时序图很漂亮但没法实现 | 只画 happy path | 补锁、幂等、状态机、补偿四件事 |
