# 技术方案生成

## 这个技能解决什么

把一个 PRD（或一组需求 / 故事）变成一份可以直接开工、也可以直接放进 AI 上下文窗口的技术实施方案。

产出不是“设计说明”，而是**施工图**：需求边界、能力事实、数据模型、接口、核心链路、风险，全部收在同一份文档里。读的人不需要再去翻别的文档，AI 也不需要人去帮它拼接上下文。

适用场景：

- vibe coding 项目，按“关联故事”拆成多份技术方案
- 一份方案覆盖 1–6 个故事，对应一个可独立验收的交付批次
- 用户已有自己的模板，需要按模板生成或补齐，而不是换一套结构

## 开工前先读

- `references/template.md` — 必须逐节照用的文档骨架。**用户已有模板时，以用户模板的章节名、编号和顺序为准，只补字段，不重排。**
- `references/methodology.md` — 为什么这样设计：自包含、行号锚定、多故事、事实先于设计。
- `references/quality-gates.md` — 交付前的自检清单。

## 工作流

### 1. 锁定输入与交付批次

先拿到 PRD 原文（链接或文件）、故事列表、涉及的端、适用商家 / 租户、上线批次。不要凭记忆或二手描述开工。PRD 是飞书文档就用可用的文档工具抓取（例如 `lark-cli docs +fetch --doc <url> --doc-format markdown`）；抓不到就请用户导出或粘贴，不要猜内容。

判断哪些故事该装进同一份文档：建一个“故事 × 共享表 / 共享接口”矩阵，两个故事共享至少一张表或一个接口 → 同一份；否则分开。不要只按“同一个大需求”合并，那是需求关联，不是技术关联。

一份文档 = 一个可以独立验收的交付批次，通常 3–6 个故事、≤15 页、一条能端到端跑通的链路。超过就按上线批次再切，不要往里堆。只有一个故事也照用本结构，只是“所含故事”只有一行。

### 2. 拆需求并锚定原文

逐条拆 2.1 表。每条需求必须能回到 PRD 的“标题 + 行号”。行号是反幻觉的锚：写不出来，说明还没读到位，或者这条需求是你自己加的。

标注端（H5 / 小程序 / App / 后台 / 服务端）和技术落点。编号只是文档内索引，不能替代行号。

明确写下“不做”的边界。范围边界比功能列表更能防止 AI 扩写。

把 PRD 里模糊、矛盾、缺数据的地方集中到 2.3，先向用户确认，或明确标“待确认（谁 / 何时 / 不确认影响什么）”。不要自己补设定。

### 3. 先核验事实，再画架构

对方案依赖的每一个有赞能力、三方能力（支付、短信、物流、开放平台接口等）逐条核验。结论只能是四种：**可用 / 受限 / 不可用 / 待确认**，并附验证方式和依据链接。

能力核验必须排在总体架构之前：前提是假的，后面整篇设计都白做。查不到就写“待确认”，不要用“应该可以”。

### 4. 设计模块与职责

4.1 表只列本方案涉及的模块，给每个模块一个稳定编号（M1…Mn），写清职责、关键设计点、已定决策。职责里用一句话写清“不负责什么”，这比单独加一列更能逼出边界。

模块必须落到可实现的类命名，不能只写“订单服务 / 商品配置”这类领域泛称。后端模块写 Service 接口名（如 `InstallmentConfigService`、`InstallmentPayService`），前端模块写页面 / 组件名（如 `InstallmentH5Page`）。Service 命名列是 AI 生成代码时的落点，也是评审判断模块是否真的可实现的依据；一个模块对应多个 Service 时拆成多行，不要挤在一格里。

不强制单独画架构图：架构由“职责模块表 + 时序图参与者”表达。如果画图，参与者必须能对上模块编号。

### 5. 设计数据模型

先让 AI 出完整 DDL 草稿，再按三刀修剪：命名偏好、类型规范、业务字段精减。DDL 是要直接跑、直接喂给 AI 生成代码的产物，单独成文件（如 `D1-schema.sql`），同时在文档 5 节为每张表放一段完整的 `CREATE TABLE` SQL 代码块（以 `-- §DDL-n` 开头），字段、类型、注释、默认值、唯一键、索引写全，并与 SQL 文件保持一致。不能只写“新建 xxx 表，字段：id、状态……”或只给一句段号引用；文档里的代码块要能直接复制建表。

金额用分（bigint），时间用 `datetime(3)`，主键 / 租户 / 软删 / 索引命名统一。枚举、状态机、幂等键、唯一键都要落到表或约束上，不要只写在文字里。

多故事共享的表只设计一次，在最早需要它的故事节里写全，其他故事只写差异。

### 6. 设计接口与链路

接口表至少包含：编号、方法、路径、说明。共享接口在首次出现的位置写全，其他位置只写“复用 B1”；故事编号和“首次定义 / 复用”写进说明列。

重点接口给请求 / 响应示例；字段名、类型、错误码、幂等语义要具体。

核心链路时序图是**技术密度下限**，不是示意图。必须把并发、幂等、状态机、异常补偿四件事落到图上：锁粒度、重复请求、超时 / 重试、回调验签、金额校验、失败回滚、重复支付、告警。只画 happy path 视为没写完。

每个参与者 / 节点标注所属故事（如 `【S1】`），让多故事文档仍可分段阅读。

### 7. 写风险与附录

风险项是“后果登记”，不是“未知清单”：写这个功能会带来什么兼容问题、异常兜底、技术债、运营成本，以及归属哪个故事、是否阻塞上线、怎么兜底。

附录 B 挂上本方案引用的官方文档 / 接口文档 / 数据字典链接，保证事实可回查。

结论摘要最后写：做什么、关键结论、明确不做什么。它应该能在 30 秒内让评审判断要不要继续读。

### 8. 自检后交付

按 `references/quality-gates.md` 逐项过，每项标 `PASS` / `FAIL` / `N/A`。`FAIL` 要么修，要么在交付说明里写明“已知缺口 + 不修的原因”。

默认输出到 `docs/技术方案/`，项目已有文档目录或飞书目录时从项目约定；文件名 `D{n}-{批次名}.md`，DDL 同名 `.sql`。

交付时说明：覆盖哪些故事、哪些结论是待确认、下一步最该确认的三件事。不要把“文档写完”当成“方案成立”。

## 评审已有方案

用户让你 review、审查或补齐一份现成方案时，不要从头重写，也不要只给“整体不错”。

1. 先读 `references/quality-gates.md`，按同一套标准找问题。
2. 输出按严重程度分级：**阻塞**（需求无法回查、能力无依据、时序缺关键异常分支、数据模型撑不起主链路）→ **高风险**（范围蔓延、模块边界不清、幂等 / 并发 / 状态机漏洞、风险无兜底）→ **建议**（结构、可读性、字段补充）。
3. 每条写清位置（章节 / 行号）、问题、证据、建议怎么改。能直接改的，用户明确让你改再动文件；只 review 时不要改原文件。
4. 如果用户要“补齐”，只补字段和缺失章节，保留原章节名、编号和顺序。

## 写作规则（这些是踩过坑的）

- **自包含优先于去重。** AI 的输入边界就是这一份文档；需要的表结构、接口、错误码、约定都当场写一遍，不要只给引用或指向。
- **不编需求、不编能力、不编行号。** 任何不能回查的断言，要么删掉，要么标“待确认”。
- **具体压过抽象。** 字段名、类型、约束、状态、错误码、锁的 key、幂等键、超时时间、重试次数、告警级别。评审能直接挑错，AI 能直接实现。
- **表格优先于长段落，时序图优先于架构图，一条链路优先于模块罗列。**
- **保留用户模板的章节名、编号和顺序。** 只做字段级补充（故事列、模块编号、Service 命名、风险归属、DDL 引用与表 SQL 代码块），不重排章节。用户说自己的模板好，就按用户的来。
- **多故事文档要能分段喂给 AI。** 每个故事节可独立阅读，公共层只出现一次；故事编号稳定（S1、S2…）。
- **待确认项要写清“谁确认、何时确认、不确认会影响什么”**，不要只写 TBD。
- **默认中文；用户用英文写就跟着英文。** 保留用户模板里的术语和章节名，不要为了“统一”改叫法。
- **篇幅是信号。** 一份文档装 3–6 个故事、正文 ≤15 页（DDL 代码块不计）是合理的；超过说明该拆批次，而不是继续加内容。

## 不要做

- 不要把整个项目塞进一份方案；不要按“同一个大需求”当关联标准。
- 不要用自编编号体系替代 PRD 行号锚定。
- 不要在能力没核验前写架构和表结构。
- 不要只画成功链路；不要用“应该 / 大概 / 可能”描述关键事实。
- 不要用领域泛称代替 Service 命名；不要让 4.1 只有“商品配置 / 支付网关”这类无法直接对应到代码的模块名。
- 不要只列表名和字段清单；每张表必须有完整的 `CREATE TABLE` 代码块。
