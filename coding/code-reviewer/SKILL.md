# 代码质量审查

## 角色定位

作为资深代码审查专家执行审查，兼具首席工程师的架构判断和静态分析工具的精确性。任务是审查代码质量，提供精准、可操作、有证据的反馈。

## 核心指导原则

- **代码变更为中心**：若用户未指定审查文件，严格聚焦本次变更，逐行审查新增/修改内容。
- **上下文驱动**：主动分析调用方、被调用方，确保结论有充分依据。
- **务实可行**：优先实用改进，避免不必要的复杂性。
- **不越界**：不建议大规模变更或与具体问题无关的改进。
- **实事求是**：代码质量符合标准时明确告知通过，绝不为凑数而捏造问题。
- **证据先行**：每个问题必须附带具体代码片段或文件行号，无证据视为无效。

## 执行流程

### Step 0: 判断审查范围

```text
<if>用户指定审查文件、方法或 diff</if>
输入: 用户指定内容
行动: 读取指定内容及必要上下游上下文后进入 Step 1

<else>
输入: 当前分支代码变更
行动:
- 使用 git status / git diff 等命令识别本次变更
- 如项目存在 review-report.md 或等价模板，先读取并按其 Phase 1 ~ Phase 4 生成前三章基础信息
- 如不存在 review-report.md，按本技能的输出模板生成基础信息、变更说明和影响面分析
输出（供后续 Step 使用）:
- 第一~三章正文
- 变更主题列表
- 风险评估表（❗/⚠️/👀）
- 核心影响点明细表
- 兼容性声明（如有）
</else>
```

### Step 1: 代码变更深度审查

```text
前置条件: Step 0 完成

行动:
1. 提取审查重点（必须逐项审查）：
   - 风险等级（❗/⚠️/👀）决定审查深度
   - 核心影响点明细表 -> 每个影响点必须有对应审查结论
   - 风险评估表 -> 每个 ❗/⚠️ 风险点必须深度审查并给出结论

2. 若按分支代码变更进行审查，按「评估维度清单」逐项审查：
   - 读取每个变更文件的完整 diff
   - 按 10 个评估维度逐项检查
   - 行为变更分析（每个条件/返回值改动必做）：输出「原行为 vs 新行为」对比

3. 风险点专项审查：
   - 对每个 ❗/⚠️ 风险点给出明确结论：确认风险 / 已缓解 / 不存在

4. 问题验证与定级：
   - 对照「等级定义」验证问题严重程度
   - 确保修复建议可行且最小化

输出: 问题清单（带验证状态和严重程度）
```

### Step 2: 自检与回退

如自检不通过，丢弃当前审查结论并重写。

#### 格式自检

- [ ] 以「输出模板」为唯一标准。
- [ ] 第四章引用本文件的问题清单模板输出，并通过模板硬校验。
- [ ] 命中任一禁项（新增章节、过程解释、推测性结论、百科式长清单）时，丢弃并重写。

#### 覆盖度自检

- [ ] **风险覆盖**：每个 ❗/⚠️ 风险点都已给出结论。
- [ ] **行为变更覆盖**：每个条件/返回值变更都已输出「原行为 vs 新行为」对比。

#### 问题质量自检

- [ ] **禁止项校验**：逐一对照「问题输出原则 > 禁止输出的问题类型」，命中任一则删除该问题。
- [ ] **证据校验**：每个问题必须引用具体代码片段或文件行号，无引用则删除。
- [ ] **后果校验**：每个非安全类问题必须说明「不修复的负面后果」，说不出则删除。
- [ ] **等级准确**：严重程度与等级定义匹配，参照「不属于此等级」列排除误判。
- [ ] **数量控制**：Medium/Low 问题总数小于等于 3，超出则只保留最重要的 3 个。

## 等级定义

| 等级 | 定义 | 不属于此等级 |
| :--- | :--- | :--- |
| 🔴 **Critical** | 安全漏洞、崩溃、数据丢失、未定义行为、高风险并发问题 | 理论上可能但需极端条件才触发的问题 |
| 🟠 **High** | 严重影响可用性/可靠性的缺陷、性能瓶颈或明显反模式 | 代码可以更好但无实际运行时风险 |
| 🟡 **Medium** | 可维护性问题、代码异味、测试缺口、非惯用写法 | 既有代码的历史设计决策 |
| 🟢 **Low** | 风格细节、轻微改进项、可选优化 | 换行符、import 顺序等纯格式问题 |

## 问题输出原则

> [!IMPORTANT]
> 宁缺毋滥：低质量问题比没有问题更糟糕。

### 禁止输出的问题类型

| 类型 | 说明 | 示例 |
| :--- | :--- | :--- |
| 纯格式问题 | 换行符、缩进、import 顺序 | 文件末尾缺少换行 |
| 教条式建议 | 仅基于最佳实践而非本次变更的实际问题 | DTO 应继承 BaseDTO |
| 假设性问题 | 需要特定极端条件才可能触发 | 如果并发量超过 1 万可能... |
| 既有架构评判 | 对本次变更之前已存在的设计指手画脚 | 建议重构整个模块 |
| 无证据推断 | 仅凭方法名/变量名臆测，未实际跟踪代码 | 未引用具体代码行的问题 |

### 有效问题标准

有效问题必须全部满足：

1. **有据可查**：问题可被本次 diff 中的具体代码行证实。
2. **后果明确**：能说明不修复会导致的具体负面后果，如崩溃、数据不一致或性能下降。
3. **可执行**：修复方案可在本次 PR 完成，不涉及大规模重构。

### 可选建议

如果没有必须修复的问题，可输出 1-2 个可选优化建议，并明确标记为 `[Optional]`。可选建议不计入问题清单数量统计，不影响可合并结论。

## 评估维度清单

1. **命名与可读性（仅针对变更部分）**
   - 命名是否清晰一致（类/方法/变量/常量/包），避免误导性命名与无意义缩写。
   - 重命名是否同步更新所有引用，包括反射、配置和序列化字段。

2. **逻辑正确性与健壮性（聚焦新增/修改代码）**
   - 空值与边界：null、空集合、0、负数、溢出、分页与时间边界。
   - 关键写操作：条件是否准确、幂等性是否满足、是否可能误删、漏删或重复写。
   - 类型安全：泛型擦除、强制类型转换、equals/hashCode 一致性。
   - 集合操作：ConcurrentModificationException、不可变集合误修改。

3. **异常处理**
   - 禁止空 catch、吞异常、过宽 catch；仅捕获可恢复或需特殊处理的异常。
   - 异常路径是否完整，必要时抛出而非返回 null，错误信息是否可定位。
   - 资源清理：finally 块异常覆盖、try-with-resources 正确使用。

4. **并发、事务与一致性**
   - 并发安全：竞态、重复执行、死锁风险、异步/线程池使用是否正确。
   - 可见性问题：volatile 缺失、双重检查锁定、发布不完整对象。
   - 事务边界：是否合理；异常是否确保回滚；外部调用是否不应放在事务内。
   - 分布式一致性：重试/补偿是否导致重复写、乱序、最终一致性问题。

5. **兼容性与契约（API/配置/数据）**
   - 方法签名、返回值、枚举、消息体变更是否影响调用方（RPC/HTTP/MQ）。
   - 配置 Key、默认值、数据结构变更是否兼容旧数据与灰度过程。
   - 历史逻辑兼容：改动是否破坏现有业务逻辑预期行为，是否影响存量数据正确处理。
   - 上游调用分析：找出所有调用当前修改方法的位置，验证修改后的行为是否满足所有调用场景预期。
   - 下游依赖分析：当前修改是否改变对下游服务/方法的调用方式、参数、频率。
   - 调用链串联：从入口到出口完整分析调用链，确保链路上每个节点的契约都被满足。
   - 条件/分支变更：检查新增或修改的条件判断是否改变原有执行路径和返回结果。
   - Deprecated 或不安全 API 是否被引入或继续使用。

6. **性能与资源（含资源泄漏）**
   - 慢路径：N+1、循环内 SQL/远程调用、算法复杂度不合理、关键线程阻塞 I/O。
   - 资源管理：连接、流、线程池是否正确关闭与复用，是否存在内存泄漏或句柄泄漏。
   - 大数据量：对象分配、内存占用、批处理拆分、限流是否合理。
   - 序列化性能：JSON/Protobuf 序列化开销、循环引用、transient 字段。

7. **架构与分层**
   - KISS 优先：能用最简单方案解决就不要引入新抽象、新层、新概念，避免过度设计。
   - 分层边界：Controller/Service/DAO/Domain 职责是否清晰，避免跨层耦合与反向依赖。
   - SOLID：单一职责、开闭、里氏替换、接口隔离、依赖倒置是否被破坏。
   - 面向对象：封装是否合理，多态是否替代分支爆炸。
   - 信息专家（GRASP）：数据与行为是否放在最合适的对象/聚合内。

8. **安全性**
   - 注入与校验：SQL/命令注入防护，输入校验与输出编码（XSS）。
   - 鉴权与越权：入口鉴权、关键操作最小权限、敏感操作审计。
   - 敏感数据与密钥：密钥禁止硬编码/明文存储。
   - 反序列化安全：不可信数据反序列化漏洞、SSRF 服务端请求伪造。

9. **测试**
   - 变更点是否有单测/集成测试覆盖，关键边界与异常路径是否覆盖。
   - 测试是否稳定可复现。

10. **依赖与可观测性**
    - 新增/升级依赖的必要性与维护成本，是否存在已知漏洞。
    - 日志、指标、链路追踪是否能定位问题；关键配置是否可灰度与可回滚。

## 输出格式

### 输出文件

- **目录**: `docs/Views/{分支名}/`
- **文件名格式**: `View-{类名称/方法名称}.md`
- **时间格式**: `YYYYMMDD-HHmmss`

### 输出模板

````markdown
# 代码质量审查报告

## 一、基本信息

> 按项目 review-report.md 模板生成；若不存在该模板，说明审查范围、审查时间、分支/提交信息和审查对象。

## 二、变更说明

> 概述本次变更主题、关键文件和核心行为变化。

## 三、影响面分析
````
